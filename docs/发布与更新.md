# 维护者发布流程

公开仓库是唯一对外发布源。不要直接提交个人安装目录，也不要将包含原始测试截图的私有工作树整份推送。

1. 在公开源码中完成改动，检查 diff，保留现有数据与连续采集规则。
2. 更新 `Directory.Build.props` 中的 `Version`、App csproj 的 `InformationalVersion`（如 `0.4.1-zhCN`），同时维护 `CHANGELOG.md`。
3. 运行 `pwsh ./tools/Build-WindowsRelease.ps1`。该脚本做隐私与数据检查、更新服务回归、fresh install/保留检查、自包含构建、ZIP 内容检查和 SHA256 生成。
4. 审阅并提交源码。推送 main 后 GitHub Actions 会运行公开验证。
5. 确保已登录 GitHub 并可推送，运行 `pwsh ./tools/Publish-Release.ps1`。它要求工作树已提交、当前分支为 main、版本标签尚不存在，再推送源码与 `vX.Y.Z` 标签。
6. 标签触发 Release workflow；成功后发布 `GwentChronicle-Windows-x64.zip` 和同名 `.sha256`。检查 Actions 结果及 Releases 附件，再通知用户。

也可手动执行：

```powershell
git push origin main
git tag -a v0.4.1 -m "Release 0.4.1"
git push origin v0.4.1
```

软件内更新读取固定仓库的 `/releases/latest`。只接受 `vX.Y.Z` 正式版本（忽略 draft/prerelease），只提供高于当前版本的版本，下载 ZIP 后核对随该发行提供的 SHA256。此校验检测完整性，不等同于代码签名；发布账号与仓库权限仍由维护者保护。

不会自动把任意本地改动上传到 GitHub，也不会用计划任务盲目同步个人数据。后续改动需要审阅并发布标签；一旦正式发行成功，已安装用户可在设置中自行检查与下载。

## 数据隔离

成品 ZIP 中不允许有 `GwentVision/cache`、对局、设置、截图、诊断、私钥或本机路径。公共出厂数据只放 `GwentVision/defaults/cache`，启动时仅复制缺失文件。公共赛事牌表放 `GwentVision/data/community`，由用户主动导入。

不要把旧用户的 deck-library、settings、姓名资料或校准写进 defaults。更新不能覆盖使用者的运行时库，也不能自动终止采集会话。修改默认资料时仍须检查 Sources、Occurrences、CustomName 与个人路径，不能仅靠改文件名认为已经匿名化。

公开仓库不带私人像素回放资料；因此不以需要私有样例的回归命令作为 CI 必过项。公开的合成数据测试能验证更新与数据规则，不能替代真实游戏中的识别效果测试。发版前应另做适当的本地原生 UI 与游戏检查，并在发行说明如实说明未验证项目。
